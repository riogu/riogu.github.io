## Summary

The goal of my project for GSoC'26 was to improve C++ support in the `-fanalyzer`. When the project was proposed,
several features needed to be implemented in order to be able to support large sets of C++ programs, and
one of the targets that provided the most improvement was adding support for polymorphism related
features.\
The project ended up implementing
[exception subclass matching](https://gcc.gnu.org/cgit/gcc/commit/?id=672923ae05596d602c16f4bdb7449931c5e81cf5),
[virtual function devirtualization](https://gcc.gnu.org/cgit/gcc/commit/?id=8f1698229d33a74cda7ec9f02575172df10b2774), 
and [modeling dynamic_cast](https://gcc.gnu.org/cgit/gcc/commit/?id=2f72dcc5e6cf444a46ce48364af98adf29d3f722).
These additions let the analyzer reason about polymorphic C++ by tracking exceptions through class
hierarchies, analyzing the real callee of a virtual dispatch, and catching bugs like dereferencing the
result of a failed dynamic_cast.\
Since much of the standard library uses `dynamic_cast` or virtual methods in some form (and many common
methods throw exceptions), adding support for these features is an important pre-requisite towards bigger
goals like analyzing and modeling `std::vector` and other containers, checking iterators for
invalidation, modeling `std::variant` or `std::unique_ptr`, and others.

## Background

As a general overview, GCC's static analyzer does coverage-guided symbolic execution over gimple-SSA IR.
It builds a graph of the user's code (the "supergraph") and then explores it with a worklist, building an
*exploded graph* whose nodes are `<program point, state>` pairs.

Since it is doing *static analysis*, it never performs any transformation on the input IR. Instead, it
just walks paths and emits warnings when a path reaches a "bad" state, with the goal of providing users
with useful diagnostics about bugs or vunerabilities in their code (i.e use-after-free, double-close,
memory leaks, etc).

The state at each node includes a `region_model`, which is a representation of memory where a *store*
records bindings from `region` instances (a variable, a field, a heap allocation) to `svalue` instances
(a constant, an initial value, a pointer, the result of a binop). Values can be pointers to regions,
which means the full region representation is graph-like.

The region model also includes:
- a `constraint_manager`, which records what's known about relationships between values.
- `dynamic extents`, mapping dynamically-allocated regions to svalues (their capacities).

In practice, when the model can't determine something it stays conservative, and where it can't model a
construct at all, it stops exploring that path.

It's also important to note that the analyzer was written with the goal of being generic, being able to
support various frontends and eventually supporting LTO (which is why it works on top of gimple-SSA IR),
but each language it wants to support invariably needs many specific constructs to be modeled in order to
provide useful diagnostics, and so far it has mostly only implemented C features.\
The C++ constructs whose behaviour depends on an object's *runtime* type were not modeled (like virtual
calls, catch matching and `dynamic_cast`), so each encounter with these constructs ended analysis of that
path. In practice that meant most of a C++ program past the first virtual call or past a catch clause
couldn't be analyzed meaningfully, which doesn't allow for very useful analysis.

Luckily, all of these missing features touch on the same problem, and the analyzer already has the
infrastructure it needs to solve it. To see why, it is useful to look at what the compiler actually emits
for a polymorphic object.


### How to find the runtime type of a polymorphic object

If a class has virtual methods, every object of that class carries a `vptr`, which is a hidden pointer
member to a table of function pointers called the `vtable`:

```cpp
struct A { int a; virtual void v (); };
struct B : A { int b; };
```

```md
                          +-----------------------+
                          |     0 (top_offset)    |
                          +-----------------------+
b --> +----------+        | ptr to typeinfo for B |
      |  vptr    |------> +-----------------------+
      +----------+        |         A::v()        |
      |    a     |        +-----------------------+
      +----------+
      |    b     |
      +----------+
```
Note that the vptr doesn't point at the start of the vtable, but at the first function slot, with
`top_offset` and the typeinfo pointer sitting *above* it at negative offsets.

The important detail here is that the vtable which a `B` object's vptr points to belongs to `B`, not to `A`,
and not to whatever the static type of the pointer we're holding happens to be. Each constructor that is
called when creating a polymorphic object writes the vptr for the class it is constructing, so by the
time the most-derived constructor finishes, the vptr *is* the runtime type of the object.

Another case to consider is that, under multiple inheritance, an object ends up with more than one vptr:

```cpp
struct A { int a; virtual void v (); };
struct B { int b; virtual void w (); };
struct C : A, B { int c; };
```

```md
                          +-----------------------+
                          |     0 (top_offset)    |
                          +-----------------------+
c --> +----------+        | ptr to typeinfo for C |
      |  vptr    |------> +-----------------------+
      +----------+        |         A::v()        |
      |    a     |        +-----------------------+
      +----------+        |    -8 (top_offset)    |
      |  vptr    |---+    +-----------------------+
      +----------+   |    | ptr to typeinfo for C |
      |    b     |   +--> +-----------------------+
      +----------+        |         B::w()        |
      |    c     |        +-----------------------+
      +----------+
```

Both of them point into the *same* vtable object, just at different `top_offset`{{% sidenote %}}The
distance from this subobject back to the start of the most-derived object, which is 0 for the A subobject
at the top and -8 for the B subobject. It's what `__dynamic_cast` uses to find the most-derived object
given only a pointer to a base subobject.{{% /sidenote %}} values.
This is what makes type substitution work: passing a `C*` to a method expecting a `B*` adjusts the
pointer by 8 bytes, and the callee finds a `B` subobject there with `C`'s vptr, which lets us identify
what the original most-derived type for our object was.

In practice this means the pair (`vtable decl + byte offset into it`) carries two pieces of information
at once which we care about: the vtable's owner is the most-derived type of the object, and the offset
identifies which subobject's vptr was read.

### What `dynamic_cast` actually is

In general, a downcast or crosscast with `dynamic_cast<T*>(p)` can't be resolved statically, since the
whole point of it is that the most-derived type isn't known at the cast site. So the frontend lowers it
to a library call:

```cpp
d = __cxxabiv1::__dynamic_cast (b, &_ZTI4Base, &_ZTI7Derived, 8);
```

At runtime, libstdc++ walks the class hierarchy starting from the most-derived type (which it recovers
from the vptr, via typeinfo), looking for both the source subobject and every subobject of the target
type, while tracking the accessibility of the paths it takes. The rules it is implementing come from
[expr.dynamic.cast]/9, and boil down to two conditions on whatever target subobject is found:

1. **Exactly one** target subobject may be found, otherwise there is no unambiguous answer as to which
   one was intended.
2. It must be reachable through an unbroken chain of **public** inheritance edges.

It's worth noting that these two conditions are orthogonal: a second target found through a *private*
path still counts as a duplicate, and still makes the cast ambiguous. When either condition fails, the
result is a null pointer (or a `std::bad_cast` for the reference form).

### The point

Putting those two together, `__dynamic_cast` needs the most-derived type at runtime, and goes to
considerable trouble to get it - typeinfo subclasses, tree walks, and a pile of shortcuts to bail out
early wherever possible.

The analyzer, however, isn't at runtime. It already watched the constructor run, so the store binds the
object's vptr field to the `_ZTV*` decl like it would for any other write it saw go by, as a
`binop_svalue` over a `region_svalue` and a constant:

    cluster for: c
      _vptr.C: (&_ZTV1C + (long unsigned int)16)

Which means the dynamic type is already sitting in the model, and nothing needs to model it separately or
bolt on any dynamic-type tracking. Recovering the decl and the offset from that binding is enough for all
three features:

- for a **virtual call**, indexing the vtable initializer by `OBJ_TYPE_REF_TOKEN` gives the concrete
  callee;
- for **`dynamic_cast`**, the vtable's owner is the most-derived type, and /9 can then be run over its
  BINFOs at analysis time, yielding either a pointer to a subobject or a null;
- for **catch matching**, the same class-hierarchy machinery answers whether a handler catches a thrown
  type.

So most of the work here is reading back information the analyzer already had, plus deciding precisely
when it *doesn't* have it and the conservative answer has to be used instead. That second part ends up
being most of the difficulty, since a conjured vptr (the model's placeholder for a value it knows nothing
about, i.e. one coming from a `Base *` returned by an unknown function) or a symbolic offset both mean
the honest answer is "unknown". Saying anything stronger in those cases produces false positives, which
are generally what makes people stop using an analyzer altogether.


## Progress made

The analyzer now models exception subclass matching, virtual call devirtualization, and `dynamic_cast`.
All three patches are merged.

### Exception subclass matching - [PR analyzer/119697](https://gcc.gnu.org/cgit/gcc/commit/?id=672923ae05596d602c16f4bdb7449931c5e81cf5)

`exception_matches_type_p` previously only treated an exception as caught when the handler type and the
exception type were identical, so a handler for a base class did not match a thrown derived class.

Added an `exception_matches_type_p` langhook returning whether a handler of one type catches an exception
of another, per the analyzed language's rules. The default returns false, preserving behaviour for
frontends without exception support. The C++ frontend implements it with `can_convert_eh` (made
non-static), which keeps the analyzer language-agnostic and the catch-matching rules in the frontend -
including the cases where matching is not just derivation: ambiguous bases, private bases,
cv-qualification, pointer conversions, `nullptr`.

The implementation assumes a single language per analysis, so it does not handle LTO over mixed C and
C++.


### Virtual function devirtualization - [PR analyzer/97114](https://gcc.gnu.org/cgit/gcc/commit/?id=8f1698229d33a74cda7ec9f02575172df10b2774)

`get_fndecl_for_call` now handles `OBJ_TYPE_REF`. It reads the value bound to the object's vptr field; if
that value has the form `&vtable_decl + constant`, the vtable decl and offset are recovered and passed to
`gimple_get_virt_method_for_vtable` together with `OBJ_TYPE_REF_TOKEN` to look up the concrete fndecl in
the vtable initializer, then resolved through `ultimate_alias_target`. A conjured vptr means the dynamic
type is unknown and the call stays unresolved.

`can_throw_p` was extended to look through thunks (needed under multiple inheritance) and to check
`TREE_NOTHROW`, so `noexcept` on the resolved override is respected.

It does not enumerate possible subtypes, so when the most-derived type isn't known it won't check whether
each candidate override could throw or leak. Thunk `fixed_offset` is not applied before binding `this`,
so the interprocedural multiple-inheritance case is still imprecise; likely fixable by applying the
offset at bind time, left as follow-up.

This support is not really C++-specific - it only deals with the GIMPLE representation of BINFOs and
vtables.

### `dynamic_cast` modeling - [PR analyzer/110578](https://gcc.gnu.org/cgit/gcc/commit/?id=2f72dcc5e6cf444a46ce48364af98adf29d3f722)

`dynamic_cast` lowers to a call to `__cxxabiv1::__dynamic_cast`, so this adds a `known_function` for it.
The runtime check of [expr.dynamic.cast]/9 is evaluated statically when the dynamic type is known,
yielding either a pointer to the target subobject or a null pointer; otherwise the LHS is left conjured.
This makes bugs like dereferencing the result of a failed cast visible.

The dynamic type comes from the same vptr binding used for devirtualization: `get_vtable_from_obj` was
factored out of `get_fndecl_for_virtual_call` so both recover the `_ZTV*` decl and the byte offset into
it. The vtable's `DECL_CONTEXT` gives the most-derived type; the offset identifies which subobject's vptr
was read. Source and target class types are recovered from the `&_ZTI*` typeinfo arguments.

Both clauses of /9 are implemented as a BINFO search over the most-derived type's hierarchy, tracking
per-path accessibility. Ambiguity ignores access specifiers, and morally-virtual matches of the same type
under different virtual ancestors are distinct subobjects, so matches are deduplicated by `BINFO_OFFSET`.
Shared primary-base vtables mean the binfo owning a vptr value may be an enclosing type, so the source
subobject is found by descending the primary chain at relative offset 0.

The result is built as a concrete `offset_region` relative to the operand's base region, so it aliases
the frontend's own field accesses to the same bytes
- this is what makes `c->m == 50` provable after the cast rather than just `c != NULL`.

`known_function_manager::get_match` previously only matched functions at global scope; it now also
matches namespace `__cxxabiv1`.

Note that pre-C++26 a constexpr constructor or destructor in a class with virtual bases is rejected
outright, so the virtual-base cases of /9 have no counterpart in the existing constexpr `dynamic_cast`
tests.
